# PWA 운영 연결·배포 가이드

2026-10-30 로컬 기준 커밋은 `5d53d2d`입니다. T3·T5·T6·T10 변경은 검토용 작업 브랜치에 있으며 운영 반영을 의미하지 않습니다.

## 구현과 운영 연결의 구분

- Manifest, Service Worker, 설치 안내, 오프라인 문서가 구현돼 있습니다.
- 매물별 Push API와 UI가 구현돼 있습니다. 상태 재확인은 설정·watch 조회만 하며 자동 등록하지 않습니다. 신청은 사용자 클릭으로 기존 기기 토큰·watch·브라우저 구독을 확인하고 재사용합니다.
- 기기 토큰이 없는데 브라우저 구독이 남아 있으면 다른 매물을 보호하기 위해 자동 삭제하지 않습니다. 해제는 해당 매물의 watch만 처리하며, 실패를 성공으로 표시하지 않습니다.
- Push API 구현과 댓글 INSERT의 DB→API 전달은 별개입니다. Database Webhook과 pg_net 트리거의 운영 적용 여부는 미확인입니다. 과거 설계 SQL은 적용 증거가 아닙니다.
- `PUSH_ENABLED` 비활성 또는 필수 환경 누락 시 설정 GET은 `enabled=false`, 구독·해제·발송은 기존 503 정책을 유지합니다. 실제 운영 값은 이번에 조회하지 않았습니다.

## DB 설치와 보안

`ops/pwa-setup.sql`은 새 테이블 4개와 서버 전용 함수 3개의 일회 설치 자료입니다. **재실행 안전한 migration이 아니므로 운영 DB에서 다시 실행하지 않습니다.** 기존 schema·RLS·권한·함수·트리거 상태를 별도 승인으로 확인하고, 필요한 차이만 별도 migration으로 검토합니다.

Push 테이블 RLS, 브라우저 역할 접근 차단, 서버 역할 권한은 SQL 설계입니다. 실제 운영 적용 여부는 미확인입니다. 과거 문서의 `trades` RLS 비활성 언급도 현재 운영 확인을 대신하지 않으며, 익명 거래 정책을 임의 변경하지 않습니다.

환경 이름은 다음과 같습니다. 실제 값·키 쌍·Production/Preview 적용 범위는 승인 후 비공개로 확인합니다.

- 공개: `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_ANON_KEY`(기존 거래), `NEXT_PUBLIC_VAPID_PUBLIC_KEY`
- 서버: `VAPID_PRIVATE_KEY`, `SUPABASE_SECRET_KEY`, `PUSH_WEBHOOK_SECRET`, `PUSH_ENABLED`

현 서버는 `VAPID_SUBJECT`를 참조하지 않습니다. Secret에 `NEXT_PUBLIC_` 접두사를 붙이지 않으며, 키 재생성·변경은 이번 범위 밖입니다.

Webhook 계약은 `POST /api/push`, JSON, `Authorization: Bearer <전용 webhook secret>`, `INSERT/public/trade_comments`, `record.id/trade_id`입니다. 실제 키를 문서에 넣지 않습니다. DB 댓글 재조회·시간 제한·중복 claim은 유지합니다. 이 문서만 보고 SQL이나 웹훅을 생성하지 않으며, 공식 경로와 자체 경로를 동시에 활성화하지 않습니다.

실패의 `retry` 상태를 처리하는 자동 scheduler는 구현돼 있지 않습니다. 재호출 시 이력을 존중해야 하며, 발송 후 이력 저장 실패에서는 중복 가능성이 남습니다. `sent`는 provider 접수이며 기기 수신 보장이 아닙니다.

## 업데이트·오프라인 정책

새 Worker의 installing·waiting·controllerchange를 안내하되 `skipWaiting`, 강제 활성화 메시지, 자동 새로고침은 사용하지 않습니다. 다른 탭의 매물·댓글 작성 또는 저장 진행 상태를 알 수 없으므로, 모든 작업을 저장한 뒤 사이트 탭과 설치 앱을 모두 닫고 다시 열도록 안내합니다. 업데이트 방법 버튼도 새로고침하지 않습니다.

오프라인 문서 캐시는 `d2-offline-v2`입니다. waiting Worker의 설치가 이전 문서 캐시를 덮지 않도록 v1과 분리했습니다. 활성화 시 `d2-offline-` 접두사의 이전 캐시만 정리합니다. 매물·댓글·Supabase·인증·Push API는 캐시하지 않습니다. 저장소 실패 시 안전한 텍스트 503으로 대체합니다. HTTP 500 등 서버 응답은 오프라인 화면으로 바꾸지 않습니다.

`navigator.onLine`과 online/offline 이벤트는 참고 안내만 바꿉니다. 재접속은 사용자 클릭으로 수행합니다. 작성 중 내용이 저장되지 않았을 수 있음을 알리며, 재등록 전 저장 여부를 확인하도록 안내합니다. 실제 OS별 설치·업데이트는 별도 검증 대상입니다.

## 배포 순서 — 별도 승인 필수

1. 소스 diff, 승인 파일 범위, lock·환경 불변을 확인합니다.
2. TypeScript·ESLint·모의 검사를 수행합니다. 빌드는 운영·외부 접근 위험을 확인한 안전 환경에서만 진행합니다.
3. 실제 운영 commit/deployment와 환경 적용 범위, DB 연결 상태를 승인 후 확인합니다.
4. 이전 배포·SW 버전·환경 기준·DB 변경 유무를 롤백 기준으로 확보합니다.
5. 보고서와 diff를 제출하고 사용자 승인 후에만 Git commit/push와 Vercel 배포를 수행합니다. 이 문서는 자동 실행 명령을 제공하지 않습니다.
6. 기존 설치 사용자, 다중 탭, waiting, 작성 중 보호, 오프라인, 서버 500, 거래 읽기·도감·경험치를 검증합니다. 쓰기·구독 검사는 승인된 대상에서만 수행합니다.
7. Push 활성화, 웹훅·트리거 연결, 실제 발송은 별도 승인합니다. 코드 배포와 동시에 true로 전환하지 않습니다.

## 롤백과 긴급 중단

이전 배포 또는 diff를 되돌린 새 배포를 검토합니다. DB table 삭제, setup SQL 재실행, force Push, 사용자 저장소 전체 삭제는 하지 않습니다. Git 롤백만으로 이미 설치된 Worker가 즉시 돌아가지는 않습니다. 호환되는 SW를 새 버전으로 배포하고 기존 기기를 확인합니다.

긴급 Push 중단은 서버의 비활성 설정과 DB 전달 경로를 별도로 승인 후 중단해야 합니다. 비활성화는 이미 전송된 알림을 회수하거나 DB HTTP 요청까지 자동 중지하지 않습니다. 이번 코드 변경은 운영 설정을 변경하지 않습니다.
